# KNOT 발표 문서 — 제출용 정리본

> 에이전트가 협상하고, 크리에이터가 만들고, 예치금이 정산을 보장합니다.

KNOT은 브랜드와 크리에이터 사이의 협찬 거래를 에이전트가 실행할 수 있는 계약·검증·정산 흐름으로 바꾸는 서비스입니다. 사람이 매번 DM을 보내고, 조건을 정리하고, 송금을 확인하는 대신 각자의 Agent가 사용자가 정한 목표와 한도 안에서 협상합니다. 합의된 금액은 USDC 에스크로에 예치되고, 콘텐츠 증빙이 검증되면 마일스톤 단위로 지급됩니다.

## 1. 한 줄 정의

**KNOT is the transaction layer where brand agents contract with human creators.**

AI 에이전트는 이미 API를 사고 쓸 수 있습니다. KNOT은 그 다음 레이어, 즉 사람이 제공하는 촬영·리뷰·콘텐츠 제작 같은 서비스를 에이전트가 계약하고 정산할 수 있게 만듭니다.

## 2. 타깃 기관 / 기업 / 개인

| 구분 | 타깃 | 왜 필요한가 |
|---|---|---|
| 기관 | Solana, Google Cloud, Agentic Commerce 생태계, 크리에이터 커머스 인프라 운영 주체 | 에이전트가 사람의 서비스를 구매하는 거래 표준과 결제·검증 레이어가 필요합니다. |
| 기업 | 반복 협찬을 운영하는 D2C 브랜드, 소형 마케팅팀, 크리에이터 대행사, 커머스 플랫폼 | 제안 검토, 조건 협상, 정산 확인에 드는 운영 비용을 줄여야 합니다. |
| 개인 | 마이크로 크리에이터, UGC 제작자, 인플루언서, 1인 스튜디오 | 제안 조건을 매번 직접 확인하지 않고, 작업 완료 후 미수금 걱정 없이 정산받고 싶습니다. |

MVP의 첫 시장은 `제품 1개 × 브랜드 1개 × 크리에이터 1명 × 콘텐츠 1개 × 마일스톤 1개`입니다. 넓은 마켓플레이스보다 한 건의 협찬 거래가 실제로 끝까지 도는 것이 핵심입니다.

## 3. 해결 문제

크리에이터 협찬은 정찰제 상품 구매가 아닙니다.

- 얼마를 지급할지 정해야 합니다.
- 릴스, 숏츠, 게시글 등 작업 범위를 정해야 합니다.
- 업로드 기한과 사용권을 합의해야 합니다.
- 결과물이 조건을 충족했는지 검증해야 합니다.
- 선입금과 후불 사이의 신뢰 문제를 해결해야 합니다.

기존 방식은 DM, 스프레드시트, 계약서, 계좌 송금이 섞여 있습니다. 에이전트를 붙여도 마지막 정산을 사람이 확인하면 자동화가 끊깁니다. KNOT은 협상부터 에스크로, evidence 검증, 정산까지 하나의 거래 타임라인으로 묶습니다.

## 4. 도입 시나리오

### 브랜드

1. 브랜드가 제품 URL과 작업 조건을 입력합니다.
2. Brand Agent가 후보 Creator를 찾고, 필요하면 외부 검증 API를 호출합니다.
3. Brand Agent가 Creator Agent에게 제안합니다.
4. 예산 한도 안에서 가격, 작업 범위, 기한, 사용권을 협상합니다.
5. 합의가 생성되면 브랜드가 지갑으로 USDC를 에스크로에 예치합니다.
6. 콘텐츠 증빙이 검증되면 정산 상태와 Explorer 링크를 확인합니다.

### 크리에이터

1. 크리에이터가 최소 단가, 가능한 포맷, 일정, 금지 조건을 설정합니다.
2. Creator Agent가 브랜드 제안을 대신 검토합니다.
3. 조건이 맞지 않으면 counter offer를 보냅니다.
4. 합의된 작업과 정산 예정 금액을 대시보드에서 확인합니다.
5. 게시물 URL을 제출합니다.
6. 검증이 통과하면 USDC를 수령합니다.

## 5. 아키텍처 다이어그램

KNOT은 세 개의 실행 경계를 분리합니다.

- Product API: 인증, 프로필, 매칭, 계약, 에스크로 오케스트레이션
- Creator Agent Service: 에이전트 협상 메시지 수신과 Creator 정책 평가
- Web3 Gateway: 트랜잭션 생성, 서명 검증, 잔액 변화 검증

## 6. 블록체인 내러티브

KNOT이 블록체인을 쓰는 이유는 web3라는 이름 때문이 아닙니다. 에이전트가 사람의 서비스를 계약하려면 돈을 조건부로 묶고, 결과가 확인됐을 때 프로그램이 지급할 수 있어야 하기 때문입니다.

### 에이전트에게는 은행 계좌가 없습니다

에이전트가 실제 거래를 실행하려면 단순 추천을 넘어 비용 집행과 조건부 지급까지 다뤄야 합니다. 기존 송금 흐름만으로는 예산 한도, 증빙 확인, 자동 정산을 한 타임라인에서 다루기 어렵기 때문에 프로그램이 검증할 수 있는 지갑과 자산 흐름이 필요합니다.

### 세 겹의 온체인 구조

| 레이어 | 역할 | 제품에서 보이는 증거 |
|---|---|---|
| Agreement hash | 협상 결과를 정규화해 나중에 바꿔 말하기 어렵게 만듭니다. | terms hash, Agreement detail |
| Anchor escrow | 브랜드 USDC를 vault에 잠그고 조건 충족 시 Creator에게 지급합니다. | escrow PDA, vault, funding tx, release tx |
| pay.sh / x402 | Agent 운영 비용과 Creator 보상 예치금을 분리합니다. | payment event, receipt 또는 SKIPPED 사유 |

### 왜 Solana / USDC인가

Solana는 소액·고빈도 결제와 빠른 확정이 필요할 때 맞습니다. 협찬 검증과 정산은 건당 금액이 작고 반복됩니다. 수수료가 크면 Agent가 필요할 때마다 검증 API를 사는 모델이 성립하지 않습니다.

USDC는 협상 금액을 안정적으로 보존합니다. 변동 자산으로 에스크로를 걸면 정산 시점에 다시 협상해야 하고, 그러면 자동화가 깨집니다.

## 7. 데모에서 보여줄 장면

1. 브랜드 계정으로 로그인
2. 프로모션 생성
3. Creator 탐색과 에이전트 협상 메시지 확인
4. 계약 상세에서 지갑 연결
5. USDC 에스크로 예치
6. 크리에이터 계정으로 로그인
7. 체결된 협상과 해야 할 작업 확인
8. 콘텐츠 URL 제출
9. evidence 검증과 마일스톤 정산 확인
10. Explorer에서 funding / release transaction 확인

## 8. 증명된 것과 경계

증명된 것:

- 실제 계정 로그인
- 역할별 온보딩과 대시보드
- Promotion 생성
- HTTP 경계를 넘는 에이전트 협상
- 계약 생성과 terms hash
- 브랜드 지갑 기반 escrow funding transaction prepare/confirm
- evidence 제출과 verification state
- Web3 Gateway 기반 release prepare/confirm 및 자동 정산 경로
- 시뮬레이션 receipt를 성공으로 처리하지 않는 검증 정책

명확히 말해야 하는 경계:

- MVP는 Solana test network 전용입니다.
- Creator 보상 정산에는 pay.sh를 쓰지 않습니다.
- pay.sh는 Agent 운영 결제, 즉 외부 검증 API 호출용입니다.
- 배포 환경에서 pay.sh resource가 `replace-me`이면 `SKIPPED`로 표시해야 하며, 결제 성공처럼 말하면 안 됩니다.
- 노쇼 보증금, 캘린더 조율, 마켓플레이스, 상세 평판 그래프는 다음 단계입니다.

## 9. 발표용 30초 스크립트

인플루언서 마케팅에서 진짜 병목은 매칭이 아니라 정산입니다. 브랜드는 선입금이 무섭고, 크리에이터는 미수금이 무서워서, 사이에 항상 사람이 낍니다.

KNOT은 브랜드 에이전트와 크리에이터 에이전트가 직접 협상하게 하고, 합의된 금액을 Solana USDC 에스크로에 잠급니다. 콘텐츠 게시 증빙이 검증되면 프로그램이 마일스톤을 릴리즈하고 크리에이터 지갑으로 정산합니다.

외부 검증 API 비용과 크리에이터 보상금은 서로 다른 결제 레일로 분리됩니다. 사람은 목표와 한도를 정하고, 에이전트는 협상을 진행하며, 예치금은 정산 신뢰를 보장합니다.
